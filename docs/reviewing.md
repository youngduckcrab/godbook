# 검토자 지침

작성자가 쓴 글에서 오류를 찾는 에이전트(보통 opus)의 작업 설명서다. **파일을 고치지 않는다.** 찾아서 보고만 한다. 칭찬은 쓰지 않는다.

## 먼저 읽을 것

1. 이 문서.
2. `docs/conventions.md` — 표기, 약속, 받아들인 사실, 아직 없는 도구. 증명의 근거를 따질 때 기준이 된다.
3. `docs/writing.md`의 "글쓰기 규칙", "증명 기법 항목", "검토에서 자주 나온 지적" — 작성자가 지켜야 하는 것.
4. 지시문이 준 출처 요약 파일(있다면)과 출처 텍스트. 요약은 길잡이일 뿐이다. `loc`과 `note`는 출처 텍스트에서 직접 확인한다.

## 무엇을 보는가

글을 믿지 말고 처음부터 다시 따진다. 항목마다 아래 여섯 가지를 본다.

**1. 수학**
- 진술이 참인가. 한정 기호와 그 순서, 변수의 범위, 빈 경우(공집합, 0, 1, 원소 하나), 정의가 양방향인가.
- 증명의 모든 단계에 근거가 있는가. 근거는 `requires` 항목의 `:::statement`, 진술의 가정, `docs/conventions.md`의 받아들인 사실, 또는 그 증명 첫머리에 이름 붙인 목록이어야 한다. 다른 항목의 직관·예시에만 있는 것을 인용하면 지적한다.
- 순환이 없는가. 증명 본체뿐 아니라 덧붙인 설명 문장이 결론을 전제로 하지 않는가.
- 진술의 가정이 증명에서 어디에 쓰이는가. 쓰이지 않는 가정, 몰래 쓰는 가정이 없는가.
- 진리표의 모든 칸, 예시·반례·확인 질문의 모든 수치를 다시 계산한다. 작은 관계와 함수는 순서쌍을 모두 나열해 확인한다.
- 증명 기법 항목(`kind: method`)은 틀이 쓸 수 있는 꼴인지, "왜 올바른가"가 정직한지(받아들이는 원리를 증명인 것처럼 쓰지 않는지), "흔한 실수"가 정말 실수인지 본다.

**2. 출처**
- `loc`의 절 번호, 정의·정리·식 번호, 인쇄 쪽수를 출처 텍스트에서 확인한다. 쪽 경계 근처는 쪽 머리글로 확인한다.
- 진술이 출처와 수학적으로 같은가. 다르면 `note`에 밝혔는가.
- 출처가 말하지 않은 것을 출처에 돌리지 않았는가. "출처는 ~하지 않는다"는 부정 주장도 확인한다(범위를 한 절에서 책 전체로 넓혀 틀린 적이 있다).
- `note`의 "새로 만들었다"가 사실인가. 출처의 예에서 글자나 수만 바꾼 것을 찾는다.
- 출처의 문장을 옮기거나 번역한 곳, `:::english`가 출처 문장과 같은 곳을 찾는다.
- 역사 서술은 문장마다 인용한 출처 원문과 대조한다. 번역어도 본다.

**3. `requires`**
- 본문(예시와 확인 질문 포함)에서 쓰는데 빠진 항목, 적혀 있는데 쓰지 않는 항목. 순환. 단원의 `concepts` 순서가 선행 관계를 지키는가.

**4. 독자**
- 독자는 지시문이 말한 단원까지만 배웠다. 정의하지 않은 용어·기호, 범위 없는 변수, 변수가 남은 문장의 참·거짓 단정, 틀린 일반화("항상", "모든", "~뿐", "~해야"), 맞지 않는 비유(비유의 각 부분이 정의의 어느 조건에 해당하는지 따진다), 어색하거나 표준이 아닌 한국어 수학 용어.
- 확인 질문이 본문의 예시·반례를 그대로 다시 묻지 않는가.

**5. 일치**
- `:::statement`와 `:::english`가 문장 단위로 같은 내용인가. `summary`가 진술과 맞는가. 한 방향으로 읽히는 "when"/"~이면"이 양방향 정의를 옮긴 것은 아닌가.

**6. 화면**
- `[[id]]`는 대상 항목의 `title` 전체로, `[[id|표시말]]`은 표시말로 보인다. 링크가 든 문장을 보이는 대로 읽어 조사와 문장이 맞는지 본다.
- 머리말이 YAML 로 제대로 읽히는가. `summary`·`title`에 수식이 없는가.

`npm run check`를 돌려 통과 여부와 경고를 확인한다. 경고가 남아 있으면 지적에 포함한다.

## 심각도

- **ERROR** — 수학적으로 또는 사실로서 틀렸다. 인용 위치가 틀렸다. 한국어와 영어의 뜻이 다르다. 거짓인 문장이 있다.
- **WARN** — 오해를 부른다. 증명에 근거가 빠졌다. 뒷받침되지 않는 주장. 규칙 위반(`requires` 누락, 출처 예의 무표기 차용, 미정의 기호, 틀리게 보이는 링크로 뜻이 달라지는 경우).
- **NIT** — 표현, 문단 길이, 조사, 일관성.

판정: ERROR와 WARN이 없으면 **PASS**, 있으면 **NEEDS-FIX**. 지휘자가 정해야 할 일(여러 항목에 걸친 약속, 진술을 좁힐지 등)은 "지휘자 확인 사항"으로 따로 적는다.

## 보고

지시문이 준 경로에 보고서 파일을 쓰고(Write 도구), 같은 내용을 답으로도 낸다. 작성자는 그 파일을 직접 읽는다.

```
# <단원> 검토 (N차)

요약 한두 문장: ERROR/WARN 수와 가장 중요한 것.

| 파일 | ERROR | WARN | NIT | 판정 |

## 여러 파일에 걸친 지적   (있을 때만)

## <파일 이름> — PASS / NEEDS-FIX
확인해서 맞은 것: (다시 계산한 것, 대조한 쪽수를 짧게)
1. **WARN** — "문제가 되는 글을 그대로 인용"
   - 왜 문제인가.
   - 고칠 방법: 구체적인 문장이나 조치.
```

- 지적마다 문제의 글을 **그대로 인용**한다. 작성자가 찾을 수 있어야 한다.
- 고칠 방법을 구체적으로 적는다. 문장 수준의 수정안을 주면 왕복이 줄어든다.
- 맞는 것을 길게 늘어놓지 않는다. "확인해서 맞은 것"은 다시 계산했다는 증거로 필요한 만큼만 쓴다.

## 재검토

수정본을 다시 볼 때는:
1. 이전 지적마다 해결 / 부분 해결 / 미해결을 적는다.
2. **바뀐 곳은 새 글로 보고 처음부터 다시 따진다.** 고치면서 새 오류가 들어오는 일이 잦다(범위를 넓히다 거짓이 된 문장, 바꾼 예시의 계산, 옮긴 문장의 주어).
3. 바뀌지 않은 진술과 증명은 다시 읽지 않아도 된다. 다만 진술이 바뀐 항목을 인용하는 다른 항목의 증명이 여전히 맞는지는 본다.
4. 파일별 최종 판정을 다시 낸다.

## 자주 나온 지적 (어디를 먼저 볼지)

여덟 단원의 검토에서 수학적 오류는 거의 나오지 않았다. 지적은 아래에 몰렸다. 많이 나온 순서다.

1. 증명 없이 쓰는 작은 사실이 이름 없이 쓰인다 (정수의 순서, 부등식, 분배법칙).
2. `note`가 "새로 만들었다"고 하지만 출처의 예와 구조가 같다.
3. `requires` 누락 (예시·확인 질문에서만 쓰는 항목).
4. 정의가 한 방향이거나, 뒤 증명이 쓰는 꼴이 진술에 없다.
5. 설명 문장의 틀린 일반화, 특히 단원 연결 글.
6. 링크가 틀리게 보인다. 조사가 안 맞는다.
7. 다른 항목의 예시에만 있는 사실을 인용한다.
8. 변수 범위가 없거나, 원소 이름과 변수 문자가 겹친다.
9. 출처에 없는 것을 출처에 돌린다. 역사 서술에 이 사이트의 판단이 섞인다.
10. 고친 뒤 `summary`·`:::english`를 맞추지 않았다.
